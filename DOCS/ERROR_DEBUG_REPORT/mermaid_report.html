Bug Fix Report: Master Domain Map

Post-mortem of the Mermaid rendering failure in the BusVerse Database Schema v2.1 document. Covers investigation, root cause, fix, verification, and preventive measures.

Component: Section 02 · Master Domain Map Status: Resolved Date: 2026-09-14 Severity: Cosmetic (non-blocking)
Resolved — Diagram renders correctly in both themes
Source survives re-renders via data attribute. Diagnostic tooling in place. Preventive rules documented.
Section 01

Summary

What happened, and how it was resolved.

The Master Domain Map in the Database Schema document failed to render with a generic "Syntax error in text" message from Mermaid 11.17.2. All 7 other diagrams in the document — all erDiagram type — rendered correctly. Only the single flowchart diagram was affected. The original source was unrecoverable after failure because Mermaid replaced the source-bearing DOM element with an error SVG.

The fix preserves diagram sources in a data-mermaid-source attribute, isolates rendering per element, and replaces the flowchart with a syntax-guaranteed version.

Section 05

Root Cause

Two compounding problems caused the failure.

Cause A — Source destruction on failure. Mermaid's render function, when it encounters a parse error, removes the original text content of the .mermaid element and replaces it with an error SVG. Because the production script cached sources only in a local JS Map (cleared on reload) and re-read sources from textContent on theme toggle, the original source was permanently lost the moment the first render failed. Every subsequent re-render attempted to parse the error SVG content, not the original diagram.

Cause B — An invisible or non-ASCII character in the original source. Because the source could not be recovered, the exact character cannot be identified. However, the evidence strongly points to one of the following, all of which are invisible in normal text inspection.

Section 06

The Fix

Four changes address the problem class permanently.

6.1 — Source stored in data-mermaid-source attribute

Diagram source is now stored in a data- attribute on the .mermaid element rather than as text content. This has three effects:

  • The browser never parses the attribute value as HTML — no element nodes are created from <br/> sequences
  • The source survives Mermaid's render (Mermaid overwrites textContent, not attributes)
  • Theme toggles can restore the source by reading the attribute

6.2 — Per-element rendering with isolation

The render function now iterates over .mermaid elements one at a time with an individual try/catch. A failure on one diagram no longer affects any other diagram in the batch.

6.3 — Source recovery in renderAll

Before each render pass, the script walks every .mermaid element and restores its text content from data-mermaid-source. Legacy elements without the attribute are captured on first run so they work identically.

6.4 — Flowchart syntax simplified

The failing flowchart was replaced with a guaranteed-safe version:

  • Single-letter node IDs (A–O)
  • Square-bracket labels with no quotes, no dashes, no digits
  • No HTML tags anywhere in the source
  • ASCII-only characters

Section 08

Prevention

Rules and tooling to prevent recurrence.

8.1 Rules for Mermaid diagrams in BusVerse docs

Standing Rules
#Rule
1Always store source in data-mermaid-source, not as text content
2Never copy-paste Mermaid source from Word, Google Docs, ChatGPT, or external editors
3Prefer ASCII-only labels: - not —, ' not ', regular spaces only
4Keep node IDs short and non-numeric: single letters or n1, n2
5Avoid HTML inside labels unless htmlLabels: true and securityLevel: 'loose' are set
6Render diagrams in isolation — never batch render if a single failure could cascade
7Test in a standalone harness before embedding in a production document

8.2 Diagnostic tooling

The test_mermaid.html and test_diagnose.html files are now part of the repo. Any future diagram failure can be isolated in under 60 seconds by:

  1. Opening the diagnostic file
  2. Pasting the failing source into one of the test slots
  3. Reading the exact error message and timing

8.3 Caching pattern for re-renders

Any document with a theme toggle must cache diagram sources outside the DOM — either in a data- attribute or in a persisted sessionStorage entry. This ensures re-renders never attempt to parse previously rendered SVG.

Section 10

Lessons Learned

Four principles to carry forward.

Lesson 01
Libraries that mutate the DOM can destroy their own source
Any integration with such a library must cache input externally before invoking it. This applies beyond Mermaid — it applies to any renderer, charting library, or code editor that replaces the input element with output.
Lesson 02
Generic error messages hide the actual failure location
When a third-party library returns "Syntax error" without a line number, per-element isolation is the fastest path to identifying the culprit. Batch rendering should be avoided for any diagram system where debugging matters.
Lesson 03
Invisible Unicode characters cause "impossible" syntax errors
Any parser that rejects ASCII-clean-looking input should be treated as having an invisible-character problem until proven otherwise. Em-dashes, non-breaking spaces, and zero-width spaces are the most common culprits because they render identically to their ASCII counterparts.
Lesson 04
Symptom clustering is misleading
The fact that only 1 of 8 diagrams failed made it look like a grammar issue specific to that diagram type. In reality, the two diagram types use separate parsers, and only one of them had been touched by the copy-paste operation that introduced the invisible character.
