PROCESS DOCUMENT // v1.0

Solo Developer Workflow

The complete operating manual for building BusVerse as a solo founder. Every document to write, every artifact to produce, every gap to fill, every rule to follow. Ordered by dependency, not by time. No timelines — just "do this before that."

Version: 1.0 Status: Active Owner: Founder Team size: 1
Overview

Introduction

You are building BusVerse Real alone. No team, no code review, no on-call rotation. This changes everything about how you work — but it does not change the fundamentals. Git discipline still matters. Testing still matters. Backups still matter. Documentation still matters. These things exist to protect you from yourself. Solo developers who skip them eventually lose data, ship broken code, or burn out.

Solo is not an excuse. It is a reason to be more disciplined, not less. Nobody catches your mistakes. You must catch them yourself — through tests, backups, and documentation.

Section 01

What Changes When Solo

Understand what you lose. Then compensate for it.

Enterprise PracticeSolo Replacement
Code review by peersSelf-review before every commit
QA team testsYou write tests + manual QA
DevOps team deploysYou deploy via CI/CD
Support team handles ticketsYou handle support
PM writes specsYou write specs + code
On-call rotationYou are on-call 24/7
StandupsDaily self-check
Sprint planningWeekly self-planning

What does NOT change: Git discipline. Testing discipline. Backup discipline. Documentation discipline. Security discipline. Staging before production. All of these exist to protect you from yourself.

Section 03

Folder Structure

One structure, used from day one. Future-you knows exactly where to find or write any document.

docs/
├── 00-overview/
├── 01-architecture/
├── 02-database/
├── 03-api/
├── 04-frontend/
├── 05-flows/
├── 06-design/
├── 07-security/
├── 08-operations/
├── 09-business/
├── 10-legal/
├── 11-college/
├── decisions/          ← ADRs (architecture decisions)
├── runbooks/           ← incident response
└── assets/             ← images, diagrams

Why this structure: Numbered prefixes keep folders in order. Categories match how a developer thinks. decisions/ and runbooks/ are separate because they're consulted differently — one before coding, one during incidents.

Section 27

Solo Discipline Rules

Non-negotiable. These protect you from yourself.

Git Discipline

Commit after every working change
Push daily — local-only code is lost code
Use branches even solo — main is always deployable
Never force-push to main
Tag releases — v0.1.0, v0.2.0
Write meaningful commit messages

Testing Discipline

Write tests before you need them — especially payments, seats, refunds
Test on real devices — simulators lie
Manual QA after every feature
Load test before launch — at least 100 concurrent users
Never skip the refund test

Backup Discipline

Daily automated DB backups
Monthly restore drill — untested backups are useless
Backup off-site — not just same cloud region
Keep 30 days minimum
Test restore before launch day

Documentation Discipline

Write ADRs before big decisions
Document every environment variable
Keep README up to date
Write runbooks for incidents before they happen
Log every bug in a bug log doc

Security Discipline

2FA on every account
Secrets in password manager, never in code
Never log PII — mask phone, email, ID
Rate limit every endpoint
Verify every webhook signature
Rotate API keys quarterly

Burnout Prevention

Take one full day off per week — no code, no email
No deploying on Fridays
Sleep before big decisions
If stuck for 2 hours, take a break
Ask for help (Discord, Reddit, mentor)
