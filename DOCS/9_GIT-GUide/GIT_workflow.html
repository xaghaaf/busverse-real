DEVELOPER GUIDE // v1.0

GitHub Branching Guide

A three-branch model for BusVerse Real. One stable production branch, one staging branch for verified builds, one development branch for active work. Every merge is protected by CI. Every release is tagged.

Model: Three long-lived branches Owner: Solo developer Enforcement: CI + branch protection
Section 01

Three Long-Lived Branches

These branches exist forever. Everything else is temporary.

main
Production
Always stable · always deployable
The canonical source of truth. Every commit on main is a production release. It receives merges only from staging (normal flow) or hotfix/* (emergency). Direct commits to main are blocked by GitHub branch protection.
Deploys to: production URL
staging
Verified
Demo-ready · pre-production
Where verified work goes before it becomes production. A feature set merges from develop into staging once it is stable and manually reviewed. This is the branch you show to stakeholders, run integration tests against, and use to catch last-minute regressions before they touch production.
Deploys to: staging URL
develop
Active
Integration · testing ground
The default working branch. All new features and fixes merge here first. CI runs on every push. This branch is expected to be occasionally broken — it is the sandbox where changes come together before they're considered stable enough for staging.
Deploys to: preview / dev URL
Section 02

How Code Flows

Every change travels the same path. No shortcuts.

feature branch ──► develop ──► staging ──► main (work) (test) (verify) (production)
Flow Rules
RuleWhy
New work starts from developEnsures the feature is built on the latest integration state
develop merges to staging when a feature set is stableSeparates "in progress" from "verified"
staging merges to main only after full verificationProtects production from half-finished work
main never receives direct commitsEvery production change is a reviewed PR
All merges into long-lived branches happen via Pull RequestCI runs before merge; audit trail preserved
Section 03

Short-Lived Branches

Branch off develop, work, merge back into develop. Lifetime: three days maximum.

Branch Prefixes
PrefixPurposeExample
feat/New featurefeat/seat-locking
fix/Bug fixfix/refund-webhook
chore/Maintenance, toolingchore/update-deps
docs/Documentation onlydocs/api-spec-v2
refactor/Restructure without behaviour changerefactor/auth-service
test/Adding or fixing teststest/seat-lock-concurrency
perf/Performance improvementsperf/eta-engine
hotfix/Emergency fix to mainhotfix/payment-crash

Naming rule: <prefix>/<short-kebab-description>. Lowercase, hyphen-separated, descriptive but short.

Section 04

Hotfix Flow

The one exception to the normal flow. Used when production is broken and must be fixed immediately.

main ──► hotfix/critical-fix ──► main │ └──► back-merge into develop + staging
Hotfix Steps
#Step
1Branch hotfix/xyz from main
2Fix the issue, test locally
3Open PR into main — merge immediately after CI passes
4Back-merge main into staging, then staging into develop
5Tag a patch release: v1.0.1

Why back-merge matters: Without it, the hotfix is lost the next time you promote develop to main. Always merge main back into staging and staging back into develop.

Section 07

Pull Request Rules

Even solo, always open a PR. It forces CI to run before merge and creates an audit trail.

PR checklist for every merge into a long-lived branch

Before Merging
  • Title follows conventional commit format
  • All CI checks pass
  • No console.log left in code
  • No commented-out code blocks
  • No TODO without a linked issue
  • Migration tested against local DB (if schema changed)
  • Manual smoke test completed
  • Docs updated if behaviour changed
  • No secrets in the diff

PR template

Place at .github/pull_request_template.md:

## What
Brief description of the change.

## Why
What problem does this solve?

## How
Approach taken.

## Tested
- [ ] Local dev
- [ ] Unit tests
- [ ] Manual smoke test

## Checklist
- [ ] No secrets committed
- [ ] Migration tested (if DB changed)
- [ ] Docs updated
Section 08

Commit Convention

Conventional Commits. Enforced by git hook. Bad messages are rejected before they land.

Format

<type>(<scope>): <subject>

Allowed types

feat · fix · chore · docs · refactor · test · perf · hotfix · build · ci · style · revert

Allowed scopes

api · ws · worker · passenger · driver · operator · admin · ui · types · db · auth · payments · tracking · booking · docs · infra · ci · deps · release · repo

Examples

feat(booking): add 5-minute seat lock extension
fix(payments): verify razorpay webhook signature before processing
docs(api): document refund webhook payload
refactor(auth): extract token signing into helper
chore(deps): bump prisma to 6.19.3
Section 09

Release Tagging

Tag every promotion to production. Tags are the ground truth of what shipped.

Format

v<major>.<minor>.<patch>
When To Bump
BumpWhen
majorBreaking API changes, DB schema changes requiring migration
minorNew features, backwards compatible
patchBug fixes, hotfixes

Examples

v0.1.0  — first working build
v0.2.0  — new feature: seat locking
v0.2.1  — hotfix: seat lock expiry bug
v1.0.0  — production launch

Command

git checkout main
git pull
git tag -a v0.2.0 -m "Release v0.2.0: seat locking + refund engine"
git push origin v0.2.0

Tag from main only. Never tag a branch other than main.

Section 10

Day-to-Day Commands

The commands you'll run most often.

Start new work

git checkout develop
git pull origin develop
git checkout -b feat/seat-locking

Commit work

git add .
git commit -m "feat(booking): implement seat lock acquisition"

Push branch

git push -u origin feat/seat-locking

Open PR into develop

GitHub UI → "Compare & pull request" → target branch: develop

After PR merges

git checkout develop
git pull
git branch -d feat/seat-locking

Promote develop → staging

# Open PR: develop → staging
# After merge, staging CI deploys to staging URL

Promote staging → main

# Open PR: staging → main
# After merge, main CI deploys to production
# Then tag:
git checkout main && git pull
git tag -a v0.2.0 -m "Release v0.2.0"
git push origin v0.2.0

Hotfix production

git checkout main && git pull
git checkout -b hotfix/payment-crash
# fix, commit
git push -u origin hotfix/payment-crash
# Open PR into main, merge
# Then back-merge:
git checkout staging && git pull
git merge main
git push
git checkout develop && git pull
git merge staging
git push
Section 11

Branch Sync Rules

Keep branches aligned. Stale branches cause merge pain.

Sync Scenarios
SituationAction
Feature branch is behind developgit rebase develop — keeps history clean
develop is behind stagingPR: staging → develop
staging is behind main after hotfixPR: main → staging
Both main and develop have new codeMerge main into develop via PR

Never merge develop → main directly. Always route through staging.

Section 12

What Not To Do

Common mistakes that break the workflow.

Anti-Patterns
Don'tDo Instead
Commit directly to mainOpen PR from staging
Force push to long-lived branchesForce push only to feature branches
Merge develop into mainMerge develop → staging → main
Leave a branch open for weeksMerge or delete within 3 days
Skip CI to merge fasterWait for green checks — 2 minutes
Tag a branch other than mainTag only main
Cherry-pick a hotfix instead of back-mergingMerge main → staging → develop
Use git push --force on shared branchesUse --force-with-lease on feature branches

Section 14

First-Time Setup

Create the three long-lived branches once and protect them.

# Create the three long-lived branches
git checkout -b main
git push -u origin main

git checkout -b develop
git push -u origin develop

git checkout -b staging
git push -u origin staging

# Protect on GitHub
# Settings → Branches → Add rule:
#   main:    require PR + require status checks
#   staging: require PR + require status checks
#   develop: require status checks only

After setup: make develop the default branch on GitHub. Set branch protection on all three. Configure CI workflows per branch. Now every change has a place and every merge has a gate.

Section 15

Optional Fourth Branch

Not required for solo work unless you ship multiple features in parallel.

release/*
Optional
Frozen release candidate
Created from staging when a version is ready to ship. Only bug fixes are allowed on this branch. Merged into main when shipped, then deleted. Useful when you want to freeze a build while continuing development on develop.
Example: release/v1.0.0

Flow with release branch

develop ──► staging ──► release/v1.0.0 ──► main │ └──► bug fixes applied here only
