Overview

Introduction

Every endpoint in BusVerse Phase 1, documented with method, path, auth requirements, request shape, response shape, and error codes. This is the contract between the frontend apps and the backend API. Both sides build against this document.

Why this exists: Frontend and backend are built by the same person (solo founder). This document is not a contract with a client — it's the contract with future-you. It answers "what shape does this data take?" months later without re-reading code.

Section 01

Conventions

Every endpoint follows these rules.

Core Rules
RuleValue
Base URLhttps://api.busverse.app/v1 (staging: api-staging.busverse.app/v1)
VersioningURL-based: /v1, /v2. Breaking changes = new version.
AuthAuthorization: Bearer <jwt>. Access token 15 min. Refresh 30 days via httpOnly cookie.
Content-Typeapplication/json. Multipart for file uploads.
TimestampsISO 8601 with timezone: 2026-09-13T14:30:00Z (UTC)
MoneyInteger paise. 1240 = ₹12.40
IDsUUID v4
Pagination (feeds)Cursor-based: ?cursor=xxx&limit=20
Pagination (tables)Offset: ?page=1&perPage=50
IdempotencyIdempotency-Key header on all POST mutations for money/booking. TTL 24h.
Request IDClient sends X-Request-ID; server echoes it in response.

Success Response Envelope

{
  "success": true,
  "data": { ... },
  "meta": {
    "requestId": "req_abc123",
    "timestamp": "2026-09-13T14:30:00Z"

}

Section 02

Request Lifecycle

How every request flows through the system.

Mermaid · Request Flow
flowchart TD A[Client Request] B[CDN + DDoS] C[Load Balancer] D[Auth Middleware] E[Rate Limiter] F[Route Handler] G[Service Layer] H[DB / Redis / Gateway] I[Response Envelope] J[Client] A --> B B --> C C --> D D --> E E --> F F --> G G --> H H --> I I --> J
Middleware Order
Applied top-down
  1. CDN + DDoS filter (Cloudflare)
  2. Load balancer → app instance
  3. Request ID injection
  4. Rate limiter (by IP, then by user)
  5. Auth verification (JWT signature)
  6. RBAC check (role + scope)
  7. Body validation (Zod / Joi schema)
  8. Idempotency check (if key present)
  9. Route handler
  10. Service layer (business logic)
  11. Response envelope
  12. Audit log (if mutation on money/booking)

Guest Sessions
Design decision

Guest users receive a real JWT with scope: "guest". Same auth mechanism, restricted permissions.

  • Guests can search, lock seats, book, pay
  • Guests cannot access booking history, chat, saved data, wallet
  • Guest session expires after 24 hours
  • Guests can upgrade to full account by verifying phone

Payment Adapter

The gateway field is optional. If omitted, the adapter picks the best gateway based on health and method.

Rate limit

10 requests per minute per user.

Webhook Flow
Gateways notify server directly

Client receives gateway response, then calls POST /payments/:id/confirm. In parallel, the gateway sends a webhook to POST /webhooks/:gateway. Server processes whichever arrives first; second is idempotently ignored.

Payment Success Sequence

1. Client → POST /payments              → gatewayOrderId
2. Client opens gateway checkout
3. User pays
4. Gateway → Client  (success callback)
5. Gateway → Server  (webhook: payment.captured)  ← authoritative
6. Client → POST /payments/:id/confirm  ← fast-path confirmation
7. Server → Client: booking confirmed + ticket

Webhook Handling Rules
  1. Verify signature before reading body
  2. Verify source IP against whitelist
  3. Check event ID against webhook_events table for duplicates
  4. Always return HTTP 200 (even on internal error) to prevent gateway retries
  5. Process asynchronously via job queue
  6. Log full payload for 90 days

Connection

Auth: query param ?token=<jwt>
