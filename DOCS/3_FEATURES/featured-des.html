BusVerse

Feature Descriptions — Real Platform. Every feature explained in plain language across 39 modules.

Version: 1.0 Type: Real Platform · Production Modules: 39 Status: Descriptive Spec

Introduction

This document is the companion to the feature list. Where the list names every feature, this document explains what each feature does, why it exists, and how it behaves. It is written for developers, designers, product managers, and evaluators who need to understand the platform in plain language.

Each of the 39 modules is described with its purpose, then every feature inside it is given a short, clear description. Technical terms are used only where necessary.

Read this alongside the Feature List. The list is the inventory. This document is the manual.

01

Authentication & Identity

Core

Every actor in BusVerse — passenger, driver, operator, admin, support — logs in differently and sees a different world. This module defines who they are, how they prove it, and what they can access.

Phone OTP Login AUTH-01

The primary login method for passengers and drivers. The user enters their mobile number, receives a one-time password via SMS, and enters it to log in. This removes the friction of remembering passwords and matches how most Indian apps work. OTPs expire in 5 minutes and are rate-limited to prevent abuse.

Email + Password Login AUTH-02

An alternative login for users who prefer it, and the primary method for admin and support staff. Passwords are hashed with bcrypt or argon2 and never stored in plain text. Failed login attempts are rate-limited and logged.

Google / Social Login AUTH-03

One-tap login via Google (and optionally Facebook or Apple). The user's name, email, and profile picture are imported. This reduces signup friction significantly — critical for a consumer app where every extra field loses users.

Guest Checkout AUTH-04

Users can book a ticket without creating an account. They provide name, phone, and email at booking time. They cannot access booking history, saved passengers, or support chat — those require an account. This lowers the barrier for first-time users who want to try the platform.

Profile Management AUTH-05

Users can edit their name, email, phone, and profile picture. Changes are reflected across all bookings. Profile data is used to pre-fill booking forms, reducing checkout time.

Saved Passengers AUTH-06

Users can save family members, friends, or colleagues as "saved passengers" with their name, age, gender, and ID details. When booking multiple seats, the user just picks from the saved list instead of re-entering details. Huge time-saver for frequent group travelers.

Saved Payment Methods AUTH-07

Tokenized saved cards and saved UPI VPAs for faster checkout. Card data is never stored on BusVerse servers — the gateway tokenizes it. Users can view and remove saved methods from their profile.

Multi-Device Sessions AUTH-08

Users can be logged in on multiple devices (phone + laptop, for example). Each session is tracked with a device fingerprint and IP. Users can see active sessions and log out any of them individually.

Logout All Devices AUTH-09

A single button that revokes all active sessions immediately. Used after a suspected account compromise or when the user wants a clean slate.

Driver KYC & Documents AUTH-10

Drivers upload their driving licence, ID proof, and a recent photo. These documents are verified by admin before the driver can be assigned to any trip. Expired documents are flagged and the driver is blocked until renewed.

Operator KYC & Company Docs AUTH-11

Operators upload GST certificate, PAN, company registration, and bank account details. Admin verifies each document. Only after approval can the operator list buses or create schedules.

Multiple Sub-Users per Operator AUTH-12

A single operator company can have multiple staff accounts — owner, fleet manager, accountant. Each has a role with specific permissions. This matches how real bus companies operate.

Admin 2FA & RBAC AUTH-13

Admins log in with email + password + a second factor (TOTP or SMS). Role-Based Access Control ensures Finance sees only finance, Ops sees only operations, and Support sees only tickets. Every admin action is logged with the admin's identity.

02

Search & Discovery

Core

The first thing a passenger does. This module determines how quickly they find the right bus and how confident they feel before booking.

Source + Destination + Date Search SRCH-01

The primary search box. User types origin, destination, and picks a date. Results are sorted by departure time by default. This is the entry point for 90% of bookings.

Autocomplete Stands SRCH-02

As the user types a city or stand name, suggestions appear instantly, ranked by popularity and geographic proximity. Powered by a geocoding service and a curated list of real stands. Prevents typos and mismatched cities.

One-Way / Round-Trip SRCH-03

Users choose one-way or round-trip. Round-trip searches both legs at once and can combine them into a single booking with a discount. Return date is required for round-trip.

Filters SRCH-04

Narrow results by bus type (AC, non-AC, sleeper, semi-sleeper), departure time window (morning, afternoon, night), price range, amenities (Wi-Fi, charging, water), and operator rating. Filters are sticky across searches.

Sorting SRCH-05

Sort results by cheapest, fastest, earliest departure, latest departure, or highest-rated operator. Default is a smart mix of price and rating.

Route Preview on Map SRCH-06

Click any result to see the full route drawn on a real map — origin, all intermediate stands, and destination. Helps users understand the journey before booking.

Popular Routes SRCH-07

A curated list of the most-booked routes on the homepage. Helps new users discover where they can travel.

Recent Searches SRCH-08

The last 5 searches are stored locally on the device and shown for quick re-search. Cleared on logout.

Saved / Favorite Routes SRCH-09

Users can save frequently traveled routes (e.g., "Home → Office" or "Delhi → Jaipur"). One tap from the dashboard re-searches them.

Multi-Leg / Connecting Routes SRCH-10

If no direct bus exists, the system finds connections: Bus A from origin to a hub, then Bus B from hub to destination. Shows combined fare, transfer time, and risk of missing connection.

Nearby Stands SRCH-11

Using the user's current location, the app shows stands within a configurable radius (e.g., 5 km). Useful for intracity or when the user doesn't know the exact stand name.

Return Journey Booking SRCH-12

When booking a round-trip, both legs are handled in one flow. The user picks seats on both buses and pays once. The return leg can be on a different operator.

03

Booking Flow

Core

The core transaction — how a passenger goes from selecting a bus to holding a confirmed ticket. This is the most important flow in the entire platform.

Interactive Seat Map BOOK-01

A visual 2D layout of the bus, generated from the bus model's seat configuration. Seats are colour-coded: green (available), red (booked), yellow (locked by another user), blue (selected by you), grey (blocked). Real-time updates mean everyone sees the same map. Tapping a seat selects it.

Seat Types BOOK-02

Different buses have different seat types — Seater (upright), Sleeper (berth), Semi-Sleeper (reclining), AC / Non-AC. Each type has a different price. The seat map reflects the actual layout of the chosen bus.

Female-Only Seat Option BOOK-03

On select routes, some seats are reserved for female passengers. Only female users can select them. This is a safety and comfort feature common in Indian bus travel.

Boarding + Dropping Point Selection BOOK-04

Most routes have multiple boarding points within the origin city (e.g., "Kashmere Gate", "Dhaula Kuan"). The user picks their preferred boarding and dropping points. These affect fare on some routes.

Passenger Details BOOK-05

For each seat, the user enters name, age, gender, and (on some routes) ID proof. Saved passengers can be picked from a list. Details appear on the ticket and in the driver's manifest.

Contact Details BOOK-06

The primary contact's mobile and email — used for ticket delivery, delay alerts, and refund notifications. Defaults to the logged-in user's details but can be changed per booking.

Fare Breakdown BOOK-07

Before payment, the user sees a clear breakdown: base fare × number of seats, taxes, convenience fee, any discounts applied, and total. No hidden charges. This transparency is critical for trust.

Coupon / Promo Code BOOK-08

An input field where users enter a promo code. The system validates it against rules (min fare, validity, usage limit) and applies the discount instantly. Invalid codes show a clear reason.

Atomic Seat Locking BOOK-09

The moment a seat is selected, it locks for 5 minutes. This prevents two users from booking the same seat. The lock uses Redis SET NX with TTL, falling back to a PostgreSQL unique constraint. If payment fails or the user abandons, the seat is released automatically. No two users can ever hold the same seat.

Group Booking BOOK-10

Users can select multiple seats in a single transaction. Group bookings often get a small discount. The group leader pays for all seats, but each passenger's details are captured separately on the ticket.

Round-Trip Combination BOOK-11

For round trips, the user books both legs at once. The system shows both buses, seats, and combined fare. Payment is single; tickets are issued for both legs.

Booking Confirmation BOOK-12

After successful payment, a confirmation screen shows the booking ID, trip details, seat numbers, and a QR ticket. The ticket is also delivered via SMS and email. From here, the user can view the ticket, share the trip, or set a reminder.

04

Payments

Core

Where real money moves. This module handles everything from gateway integration to refunds, with strict compliance and zero tolerance for duplication or fraud.

Multi-Gateway Support PAY-01

BusVerse integrates with Razorpay, PhonePe, Paytm, Google Pay (via UPI), and Cashfree. If one gateway is down, users can pay via another. This reduces payment failures significantly.

Payment Methods PAY-02

UPI (the most popular in India), credit/debit cards, netbanking, wallets, and EMI on select banks. Users pick whatever is convenient. UPI is shown first by default.

Payment Adapter PAY-03

A single interface that abstracts all gateways. It has three modes: Simulated (in-app fake UPI screen for demo/testing), Sandbox (real gateway in test mode with dummy money), and Live (real money). Switching modes is config-driven; no code changes.

Idempotent Payment Creation PAY-04

Every payment request carries an idempotency key. If the user retries due to a network blip, the gateway recognises the duplicate and returns the same result — never charging twice.

Payment Webhooks PAY-05

Gateways send webhooks when a payment succeeds, fails, or is refunded. BusVerse listens and updates the booking status in real time. This is how refunds are tracked automatically.

Retry Failed Payments PAY-06

If a payment fails (insufficient balance, wrong PIN, network issue), the seat lock is preserved for a short window, and the user can retry without re-selecting the seat.

Tokenized Saved Cards PAY-07

Cards are stored as gateway tokens, not raw card numbers. BusVerse never sees or stores PAN or CVV. Compliant with RBI and PCI-DSS.

Refund Engine PAY-08

An event-driven engine that listens for cancellations, checks the refund policy, calls the gateway refund API, and tracks status via webhooks. Refunds go back to the original payment method. Fully automated — no manual intervention for standard cases.

GST Invoice Generation PAY-09

Every booking generates a GST-compliant invoice showing the fare breakdown, GST rate, and BusVerse's GSTIN. Sent to the user's email and downloadable as PDF. Required for corporate and business travelers.

Duplicate Payment Detection PAY-10

If the same booking is paid for twice (e.g., due to a gateway glitch), the system detects the duplicate and auto-refunds the second payment within minutes.

Payment Receipts PAY-11

A simple receipt (distinct from the GST invoice) is sent on every successful payment. Shows amount, method, gateway reference, and timestamp. Used for expense claims and personal records.

Test Route (₹1) with Auto-Refund PAY-12

A hidden test route with a ₹1 fare used only for internal testing of the payment pipeline. Not visible in public search. Automatically refunded after payment. Excluded from analytics and settlements.

05

Tickets & QR

Core

The digital proof of a booking. This module defines how tickets are generated, delivered, scanned, and tracked through their lifecycle.

Virtual Ticket with Booking ID TKT-01

Every confirmed booking generates a ticket with a unique booking ID (e.g., BV-2026-XXXXXX). The ticket shows route, bus, seat, departure time, passenger names, and fare. Delivered via SMS, email, and in-app.

Signed QR Code TKT-02

Each ticket carries a QR code with a cryptographic signature. The driver's app verifies the signature before accepting the ticket. This prevents forgery — even if someone screenshots another person's ticket, the signature won't match the booking record.

Ticket States TKT-03

A ticket moves through clear states: Issued (just booked), Active (upcoming trip), Scanned (driver scanned it), Used (trip completed), Expired (2 hours after trip end), or Cancelled. States are visible to the user and logged for audit.

PDF Download TKT-04

The ticket can be downloaded as a PDF for printing or offline use. Includes the QR, booking ID, and all trip details.

SMS + Email Delivery TKT-05

Tickets are delivered via SMS (short link to view) and email (PDF attachment + inline QR). This dual delivery ensures the user has the ticket even if one channel fails.

Offline Viewing TKT-06

As a PWA, BusVerse caches the ticket on the device. Users can open and show the QR even without internet — critical for boarding in poor-network areas.

Re-send Ticket TKT-07

If the ticket didn't arrive or the user lost it, a "Re-send" button delivers it again via SMS and email. Rate-limited to prevent abuse.

Add to Calendar TKT-08

One tap adds the trip to Google Calendar, Apple Calendar, or Outlook. Includes boarding point, time, and a reminder 2 hours before departure.

Ticket Scan Log TKT-09

Every scan attempt is logged with timestamp, driver ID, GPS location, and result (valid/duplicate/invalid). Used for dispute resolution and audit.

06

Cancellation & Refund

Core

A transparent, time-based cancellation policy with automated refunds. This is where trust is built or broken.

User-Initiated Cancellation CAN-01

Users can cancel any confirmed booking from their "My Trips" screen. The system shows the refund amount before confirming. Cancellation is instant, and the refund is triggered immediately.

Operator-Initiated Cancellation CAN-02

When an operator cancels a trip, all bookings are auto-refunded 100%. Users are notified immediately with alternative bus suggestions. Operators who cancel frequently have their quality score reduced.

Platform-Initiated Cancellation CAN-03

In rare cases (weather emergencies, government advisories), BusVerse may cancel trips. Users get 100% refund plus a small compensation credit to their wallet.

Partial Cancellation (Group) CAN-04

In a group booking, the leader can cancel individual seats without cancelling the whole booking. Each cancelled seat is refunded per policy; the rest remain confirmed.

No-Show Handling CAN-05

If a passenger doesn't board and doesn't cancel, the ticket is marked "no-show" after departure. No refund is issued. The seat is released for potential last-minute sale.

Time-Based Refund Policy CAN-06

Refunds scale with how far in advance the user cancels: 100% if more than 24 hours, 90% for 12–24 hours, 75% for 6–12 hours, 50% for 2–6 hours, 0% within 2 hours. This balances user fairness with operational reality.

Auto Refund via Gateway CAN-07

The refund is sent back to the original payment method — UPI to UPI, card to card — automatically. No manual approval for standard cases. Refunds are initiated within minutes and typically reach the user's bank in 3–7 business days.

Refund Webhook Tracking CAN-08

Gateway webhooks update the refund status in BusVerse (Initiated → Processed → Settled). Users see the current status in the app; support sees the full timeline.

Refund History CAN-09

A dedicated screen listing all past refunds with amount, reason, status, and gateway reference. Downloadable as PDF for records.

Refund to Original Method CAN-10

Refunds always go back to the exact method used for payment. This is a legal and compliance requirement in India — no redirecting refunds to a different account.

07

Live Tracking

Core

Passengers see exactly where their bus is, when it will arrive, and can share that live with family. This is one of the most valued features for both safety and convenience.

Real GPS from Driver Phone TRK-01

The driver's phone streams its GPS location to the backend every 10 seconds. No hardware device is required — the driver app runs in the background. This keeps costs low and deployment fast.

Live Map Position TRK-02

The bus appears as a moving icon on a real map. Updates arrive every 10 seconds, and the client interpolates between them for smooth movement. Users can zoom in and see the bus on the exact road.

ETA Per Stand TRK-03

For each upcoming stand, the system shows an estimated arrival time. Recalculated every 10 seconds based on current speed, distance, and traffic.

Traffic-Adjusted ETA TRK-04

ETAs incorporate real traffic data from Google Maps, TomTom, or HERE. If congestion is detected ahead, the ETA increases automatically. No surprise delays.

Route Overlay TRK-05

The full route is drawn on the map — origin, all stands, and destination. The traversed portion is highlighted differently from the upcoming portion.

Bus Status TRK-06

The bus icon changes colour based on status: green (on time), amber (slightly delayed), red (heavily delayed or stopped), blue (at a stand). A tooltip shows details like speed and next stop.

Share Trip Live Link TRK-07

Users can send a live link to family via WhatsApp or SMS. The link opens in a browser and shows the bus's current position, ETA, and trip details — no login required. This is a critical safety feature, especially for solo travelers.

Trip Timeline TRK-08

A vertical timeline showing past stands (with actual arrival times) and upcoming stands (with ETAs). Users see progress at a glance.

Driver Info on Map TRK-09

The driver's name, photo, and rating are shown on the map. Helps passengers recognise their bus and gives a sense of accountability.

Live Bus Occupancy TRK-10

Passengers see how full the bus currently is (e.g., "32 / 40 seats filled"). Useful for understanding comfort levels before boarding.

08

Driver App

Core

The driver's daily tool. A mobile app that handles trips, GPS streaming, QR scanning, and passenger management. Designed to work with one hand, in a moving vehicle.

Phone OTP Login DRV-01

Drivers log in with their registered phone number and OTP. No password to remember. Session persists for weeks so drivers don't log in every day.

Assigned Trips View DRV-02

Shows today's and upcoming trips assigned to the driver. Each trip displays route, departure time, bus number, and passenger count. Tap to start.

Start / End Trip DRV-03

A prominent "Start Trip" button begins the journey — activates GPS streaming, opens the passenger manifest, and notifies passengers. "End Trip" closes the trip and generates a summary.

Background GPS DRV-04

Once a trip starts, GPS streams in the background even if the driver closes the app or locks the phone. Uses Android/iOS background location APIs with a persistent notification showing the app is running.

QR Scanner DRV-05

Opens the phone's camera to scan passenger ticket QR codes. Verifies signature, booking, schedule match, and scan status. Shows ✅ for valid, ⚠️ for duplicate, ❌ for invalid. Works offline against a cached list of valid bookings.

Manual Booking ID Entry DRV-06

Fallback for when the QR won't scan — a text field where the driver types the booking ID. Server validates it the same way as a QR scan.

Passenger Manifest DRV-07

A list of all passengers on the trip — name, seat, boarding point, dropping point. Groups by boarding point so the driver knows who gets on where.

Boarding / Alighting Counts DRV-08

At each stand, the app shows how many passengers are expected to board and alight. The driver marks them as boarded or no-show. Live count updates throughout the trip.

Stop Requests Handling DRV-09

When a passenger requests a stop at an upcoming stand, the driver sees an alert with the passenger's seat number. Acknowledging slows the bus and stops at the stand. Skipping notifies the passenger.

Delay Reporting DRV-10

If the bus is delayed, the driver picks a reason (traffic, breakdown, rest stop, medical) and the system notifies all affected passengers. Accurate, transparent delays build trust.

SOS Button DRV-11

A prominent red button that instantly alerts the admin team, support, and the operator with live location. Used for accidents, medical emergencies, or security threats.

Break Management DRV-12

Drivers log breaks (rest, meal, fuel) with timestamps. Break time is factored into ETA. Long breaks trigger a notification to admin for compliance with driving-hours rules.

Trip Summary at End DRV-13

After "End Trip," the driver sees a summary: total passengers, on-time percentage, delays reported, incidents. Useful for self-review and as a record for the operator.

Document Expiry Reminders DRV-14

The app reminds drivers 30, 15, and 7 days before their licence or medical certificate expires. Prevents accidental non-compliance.

Announcements to Passengers DRV-15

The driver can send short messages to all passengers on the trip — "Arriving in 5 minutes", "Next stop is X". Displayed as push notifications and in-app alerts.

Operator Panel

Core

The bus operator's business dashboard. Everything an operator needs to run their fleet and revenue on BusVerse, in one place.

Dashboard OPS-01

Overview of today's trips, total bookings, revenue, and fleet status. Recent bookings and cancellations shown live. A quick way to know the day's pulse.

Fleet Management OPS-02

Add, edit, and deactivate buses. Each bus has registration number, model, capacity, seat layout, and status (active / maintenance / inactive). Only active buses appear in search results.

Bus Registration OPS-03

Upload registration certificate, permit, insurance, fitness certificate, and pollution certificate. Admin verifies before the bus goes live. Expiry dates are tracked and reminders sent.

Seat Layout Configurator OPS-04

A visual tool to design the seat layout of each bus — rows, columns, aisle position, seat types (seater/sleeper), window/aisle, female-only. This layout appears to passengers during booking.

Amenities Configuration OPS-05

Tick which amenities each bus offers — AC, Wi-Fi, charging point, water bottle, blanket, reading light, entertainment. Shown on search results and used as filters.

Bus Photos OPS-06

Upload interior and exterior photos of each bus. Photos appear on the booking page, building passenger confidence.

Maintenance Log OPS-07

Record every service, repair, or inspection with date, description, and cost. Used for fleet health tracking and to prevent scheduling a bus under maintenance.

Route Management OPS-08

Create routes by drawing on a real map. Add stands with exact coordinates. Set distances and expected durations between stands. Routes are submitted to admin for approval.

Stand Creation OPS-09

Operators can add new boarding/dropping points along a route. Each stand has a name, coordinates, and type (regular, refreshment, transfer). Reused across multiple routes.

Schedule Management OPS-10

Create schedules — either one-time or recurring (daily, weekly). Each schedule has a bus, route, departure time, and fare. Passengers search against schedules.

Driver Management OPS-11

Add drivers to the company, assign them to trips, and track their performance. See each driver's rating, on-time %, and history.

Booking Management OPS-12

View all bookings across the fleet, filter by trip, route, date, or status. Cancel a booking (with refund) when required.

Revenue & Settlement OPS-13

Real-time revenue tracking per trip, per route, per bus. Settlement statements every 7 days showing gross bookings, deductions, and net payout. Downloadable as PDF and CSV.

CCTV Access OPS-14

Where buses have CCTV installed, operators can view live feeds and playback from the panel. Camera angles include front, middle, rear, driver, and door.

Reports OPS-15

Generate reports on bookings, revenue, cancellations, occupancy, and driver performance. All exportable as CSV or PDF for accounting and audits.

10

Admin Panel

Core

The nerve center of BusVerse. Approvals, oversight, disputes, finance, CCTV, content, and every platform-wide setting flows through here.

Dashboard ADM-01

Platform-wide metrics: active users, ongoing trips, bookings today, revenue today, pending approvals, open disputes. Customisable widgets for each admin role.

User Management ADM-02

View, search, and manage all passenger accounts. Suspend or ban users for policy violations. Reset passwords. Review booking history and refund activity.

Operator Management ADM-03

Approve or reject operator KYC. View company details, documents, and history. Suspend operators who violate policies. Track each operator's quality score and settlement history.

Bus Registration Approval ADM-04

Review each new bus — check registration, insurance, permit, fitness. Approve only if all documents are valid. Flag for re-verification when documents near expiry.

Route Approval ADM-05

Review routes proposed by operators. Check that stands exist on the map, distances are correct, and the route doesn't overlap with existing buses illegally. Approve or request changes.

Schedule Approval ADM-06

Optional gating — some platforms auto-approve schedules; others review them. BusVerse supports both modes. Admin can flag schedules for manual review based on rules (e.g., new operator, unusual route).

Booking Oversight ADM-07

View all bookings across the platform. Filter by user, operator, date, or status. Useful for investigations, refund requests, and analytics.

Refund Approval Queue ADM-08

Refunds above a threshold (e.g., ₹5,000) or flagged as suspicious require admin approval. The queue shows pending requests with reason, amount, and context.

Finance & Settlement ADM-09

Manage settlements to operators. View gross bookings, refunds, convenience fees, and net payouts. Trigger settlements manually or let the automatic scheduler handle it.

CCTV Monitoring ADM-10

Access live and playback CCTV feeds from any bus across any operator. Used for incident investigation, safety audits, and dispute resolution. Access is logged for compliance.

Notifications Broadcast ADM-11

Send push, SMS, or email messages to a targeted subset of users — by route, city, operator, or all users. Used for service announcements, weather warnings, and promotions.

Support Ticket Management ADM-12

View all support tickets, assign to agents, track SLAs, and audit resolutions. Escalations from the Support Panel land here.

Content Management ADM-13

Edit Terms of Service, Privacy Policy, FAQ, About Us, and contact information. Changes take effect immediately across all apps.

Feature Flags ADM-14

Enable or disable features for all users, specific user segments, or a percentage rollout. Used for safe deployment of new features and emergency kill switches.

Audit Logs ADM-15

Every admin action is logged with timestamp, admin ID, action, and affected record. Immutable. Used for compliance, investigations, and internal accountability.

11

Support Panel

Core

A lightweight version of the Admin Panel for support agents. Designed for speed and empathy — agents should be able to resolve most issues in one screen.

Ticket Queue SUP-01

A live queue of open tickets sorted by priority and age. Each ticket shows user, category, and SLA countdown. Agents can claim or reassign.

Live Chat SUP-02

Real-time chat with passengers who initiate support. Typing indicators, read receipts, file attachments, and chat history. Multiple chats supported simultaneously.

Canned Responses SUP-03

Pre-written responses for common questions — "How to cancel?", "Where's my refund?", "How to change seat?". Saves time and keeps answers consistent.

User Lookup SUP-04

Search any user by phone, email, or booking ID. See their recent bookings, refunds, complaints, and contact history — all on one screen.

Refund Processing SUP-05

Issue refunds within approval limits directly from the support panel. Refunds above the limit go to the admin queue.

Escalation to Admin SUP-06

Complex issues can be escalated with a single click. The admin sees the full context — chat history, user details, and reason for escalation.

Chat History SUP-07

Every chat is stored and searchable. Used for QA, coaching, and dispute resolution. Retention is configurable for compliance.

12

Notifications

Core

Every important moment in a booking triggers a notification. Delivered across multiple channels so users never miss an update.

SMS Channel NOT-01

Used for OTPs, booking confirmations, and critical alerts. Delivered via MSG91, Twilio, or Kaleyra with DLT-registered templates. Works on all phones.

Email Channel NOT-02

Used for detailed notifications, invoices, and tickets with PDF attachments. Sent via SendGrid or AWS SES with high deliverability.

Push Channel NOT-03

Real-time notifications via Firebase Cloud Messaging. Used for delay alerts, bus arrival, and refund status. Users can opt out per category.

In-App Channel NOT-04

A notification center inside the app with a badge count. All past notifications are viewable and grouped by type.

Booking Confirmed NOT-05

Sent immediately after payment success. Contains the booking ID and a link to view the ticket.

Ticket Generated NOT-06

Sent once the ticket is generated with a QR code. Includes the PDF link and a direct link to view the ticket in-app.

Trip Started NOT-07

Sent when the driver starts the trip. Passengers know the bus is moving and can begin tracking live.

Bus Delayed NOT-08

Sent when the driver reports a delay. Includes the reason and the new ETA. Users can plan around it.

Bus Arriving NOT-09

Sent 15 and 5 minutes before arrival at the user's boarding point. Reduces waiting time at stands.

Trip Completed NOT-10

Sent when the trip ends. Includes a prompt to rate the operator and driver.

Cancellation Confirmed NOT-11

Sent when a cancellation is processed. Includes the refund amount and expected timeline.

Refund Initiated NOT-12

Sent when the refund is triggered at the gateway.

Refund Completed NOT-13

Sent when the gateway confirms the refund is processed. Includes the reference number.

Payment Failed NOT-14

Sent when a payment fails. Includes the reason and a direct link to retry.

Operator Cancelled Trip NOT-15

Sent when an operator cancels. Includes refund confirmation and alternative bus suggestions.

Driver Assigned NOT-16

Sent when a driver is assigned to the trip. Includes the driver's name, photo, and rating.

Waitlist Seat Available NOT-17

Sent when a seat opens up on a waitlisted trip. Includes a link to book within the time window.

Price Drop Alert NOT-18

Sent when the fare on a tracked route drops below the user's threshold.

Promo Code Alert NOT-19

Sent when a new promo code is available for the user's frequent routes.

Safety Features

Core

Real-Time Infrastructure

Core

The backend backbone that makes everything else real-time. Without this, BusVerse is just another booking site.

WebSocket Server RT-01

Socket.IO (or raw WebSocket) pushes events to clients instantly. Passengers see bus movement, seat locks, and notifications without refreshing the page.

GPS Ingestion Pipeline RT-02

A high-throughput pipeline that receives GPS points from driver phones, validates them (speed sanity checks, geofencing), and stores them for broadcast.

Position Broadcasting RT-03

Position updates are broadcast only to users interested in that trip. Uses WebSocket "rooms" so that a passenger watching Trip A doesn't receive updates for Trip B.

ETA Calculation Engine RT-04

Recalculates ETA every 10 seconds based on current position, speed, remaining distance, and traffic conditions. Historical speed data is used for legs with no live updates.

Traffic Integration RT-05

Real-time traffic from Google Maps, TomTom, or HERE. Traffic data is used to adjust ETAs and flag delays before they happen.

Map Rendering RT-06

Maps rendered using Leaflet, Mapbox, or Google Maps. Tile choice depends on cost and coverage. Supports custom markers, polylines, and clustering.

Routing Engine RT-07

Calculates the fastest or shortest route between two points. Uses OSRM or GraphHopper (self-hosted) or Google Directions (hosted). Used when operators draw new routes and when generating ETAs.

Geocoding RT-08

Converts place names to coordinates (for autocomplete) and coordinates to place names (for stand display). Powered by Nominatim or Mapbox.

Fallback to Polling RT-09

If WebSocket connection fails (firewalls, poor networks), the client falls back to polling every 3 seconds. Ensures the app works even when real-time isn't available.

Reconnection Handling RT-10

When the WebSocket drops, the client reconnects automatically and requests any missed events. Users see a smooth experience even on flaky networks.

Compliance & Legal

Core

Everything required to operate as a legal bus aggregator in India. Documented as a readiness plan for commercial launch.

Note: These are production requirements. They are listed here so developers, founders, and evaluators can see the full legal surface area of a real bus aggregator.

Private Limited Incorporation LEG-01

Registration with MCA via SPICe+ form. PAN and TAN are issued during incorporation. Preferred over LLP for raising investment.

GST Registration LEG-02

Mandatory for any ECO (Electronic Commerce Operator) facilitating bus bookings. 5% GST is charged on all online bus bookings and remitted to the government.

Shop & Establishment LEG-03

State-level registration for any business with a physical office. Required within 30 days of starting operations.

DPDP Act 2023 Compliance LEG-04

India's data protection law. Requires consent before processing personal data, a clear notice, the ability for users to access, correct, and erase their data, and a Grievance Officer. Penalties up to ₹250 crore.

Payment Aggregator Compliance LEG-05

Use of an RBI-licensed Payment Aggregator (Razorpay, PhonePe, etc.). PCI-DSS compliance via hosted checkout. KYC of operators required. No storage of raw card data.

Motor Vehicle Aggregator Guidelines 2025 LEG-06

Central guidelines for aggregators. Requires state-wise licence, security deposit, VLTD on buses, driver verification, and CERT-In certified apps. Some states have specific variations.

Consumer Protection (E-Commerce Rules 2020) LEG-07

Requires clear disclosure of operator details, transparent refund policy, and a Grievance Officer. Recent court rulings make aggregators jointly liable with operators for service failures.

CERT-In Registration + 6hr Reporting LEG-08

Registration on the CERT-In CSITe portal before an incident occurs. Any cyber incident must be reported within 6 hours. Logs must be retained for 180 days within India.

Passenger Travel Insurance LEG-09

Minimum ₹5 lakh cover per trip, as required by aggregator guidelines. Bundled into the fare or offered as an optional add-on.

Driver Insurance LEG-10

As per the Social Security Code 2020, drivers must have a minimum of ₹5 lakh cover. Verified during driver onboarding.

Cyber Liability Insurance LEG-11

Recommended insurance covering data breach costs, legal liabilities, and regulatory fines. Not mandatory but strongly advised.

Operator Agreement LEG-12

A signed contract between BusVerse and each operator. Defines commission/convenience fee structure, settlement terms, cancellation liability, data sharing, and service standards.

Terms of Service LEG-13

Legal terms governing passenger use of the platform. Includes refund policy, cancellation policy, liability limits, and dispute resolution clauses.

Privacy Policy LEG-14

Mandatory under DPDP Act and IT Rules. Explains what data is collected, why, how it's protected, and user rights. Must be in English and 22 Indian languages if BusVerse is deemed an "intermediary".

Refund & Cancellation Policy LEG-15

A transparent policy accessible from every screen. Defines the time-based refund tiers and the process for cancellations.

Driver Agreement LEG-16

Signed agreement between BusVerse (or the operator) and each driver. Covers verification, training, insurance, and code of conduct.

Trademark Registration LEG-17

Register "BusVerse" name and logo with the Indian Trademark Registry. Protects brand identity.

Fraud Detection

Critical

Real money attracts fraud. This module catches it before it becomes a problem.

Velocity Limits FRD-01

Limit the number of bookings a single user can make per day. Anything above the limit is flagged for review. Prevents bulk fake bookings.

Duplicate Account Detection FRD-02

Flag accounts that share the same phone number, device fingerprint, or IP address with another account. Common pattern for promo abuse.

Card Testing Prevention FRD-03

Detect patterns where attackers test stolen cards by making small bookings. Block IPs and devices exhibiting this pattern.

Refund Abuse Detection FRD-04

Users who repeatedly book and cancel are flagged. Too many cancellations in a short period leads to suspension of refund privileges.

Promo Code Abuse Detection FRD-05

Detect users who create multiple accounts to exploit first-time-user promos. Auto-block these accounts.

IP-Based Risk Scoring FRD-06

Every request is scored based on the originating IP. VPNs, proxy networks, and known fraud IPs get higher risk scores.

Device Fingerprinting FRD-07

A unique fingerprint is computed per device. Multiple accounts from the same device are flagged for investigation.

Blacklist Management FRD-08

Admin can blacklist users, phone numbers, emails, IPs, and devices. All blacklisted entities are blocked from booking.

Manual Review Queue FRD-09

High-risk bookings go to a manual review queue. An admin reviews and approves or rejects before the booking is confirmed.

Auto-Block Suspicious Users FRD-10

Users with a risk score above a threshold are auto-blocked. Block is temporary by default; admin can make it permanent.

Fraud Analytics Dashboard FRD-11

Real-time view of fraud patterns — velocity, duplicates, refund abuse, promo abuse. Used by the risk team to tune thresholds.

Dynamic Pricing Engine

High

Fare calculation that responds to demand, time, and season — capped by regulation. The single biggest lever for increasing operator revenue without adding buses.

Base Fare + Demand Multiplier DYN-01

Starts from a base fare set by the operator. Then applies a multiplier based on current demand (seats sold vs total).

Time-of-Day Pricing DYN-02

Early morning and late-night buses may be cheaper. Peak hour (rush) buses may be slightly more expensive.

Festival / Holiday Surcharge DYN-03

Diwali, Holi, Eid, long weekends — demand spikes; prices adjust. Capped by regulation.

Last-Minute Premium DYN-04

Bookings made within 2 hours of departure may carry a small premium — reflecting the value of last-minute availability.

Advance Booking Discount DYN-05

Bookings made 30+ days in advance get a discount. Encourages early planning and gives operators cash flow.

Route Popularity Factor DYN-06

Higher-demand routes carry slightly higher base prices. Reflects cost of running buses on popular routes.

Regulatory Cap DYN-07

Maximum dynamic pricing is capped by law (e.g., +50% of base in some states). The engine never exceeds the cap.

Admin Controls per Route DYN-08

Dynamic pricing can be enabled or disabled per route. Some routes use flat pricing; others use dynamic.

Pricing Transparency DYN-09

The user sees the fare breakdown — base + surcharge = total. No hidden dynamic pricing.

Bus Substitution Handling

High

Operators sometimes swap the bus at the last minute. Different layout, different amenities. This module handles the fallout gracefully.

Detect Bus Substitution SUB-01

When the operator assigns a different bus to a trip, the system detects the change and flags affected bookings.

Auto Re-Seat Passengers SUB-02

If the new bus has the same layout, passengers keep their seat numbers. If different, the system assigns equivalent seats automatically.

Notify if Seat Change is Required SUB-03

If the seat number changes, the passenger is notified with the new seat. New ticket is issued.

Offer Refund if Major Change SUB-04

If the substitution is major (AC → non-AC, seater → sleeper), the passenger can choose to cancel for a full refund.

Amenity Difference → Partial Refund SUB-05

If the new bus lacks an amenity (Wi-Fi, blanket), a partial refund or wallet credit is issued automatically.

Passenger Confirmation for Major Changes SUB-06

For significant changes, the passenger is asked to confirm acceptance before the change is final. No silent downgrades.

Substitution Log SUB-07

Every substitution is logged with reason, timestamp, and affected bookings. Used to penalise operators who substitute frequently.

High

Detect Overbooking OVB-01

Notification to Affected Passengers OVB-06

Overbooking Log OVB-07

Every instance is logged with cause, impacted passengers, and resolution. Used for pattern detection.

Operator Penalty for Repeated Overbooking OVB-08

Operators who overbook repeatedly face penalties — lower quality score, higher commission, or suspension.
