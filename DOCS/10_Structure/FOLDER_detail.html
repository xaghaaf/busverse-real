Modular Folder Structure

The complete repository layout for BusVerse Real. A pnpm monorepo with Turbo, split into eight top-level concerns. Every folder has one job. Every package builds independently. Ready for the three-branch Git workflow.

Section 03

apps/

Deployable user-facing applications. One folder per panel.

Applications
FolderPurposeTech
passenger-webPassenger PWA — search, book, pay, trackNext.js 15
operator-panelBus operator dashboard — fleet, routes, revenueNext.js 15
admin-panelBusVerse admin — approvals, disputes, CCTVNext.js 15
support-panelSupport console — tickets, chat, refundsNext.js 15
driver-appDriver mobile — trips, GPS, scannerReact Native

Feature-first organization: inside each app, code is grouped by feature (features/booking/, features/tracking/) not by type. Each feature owns its components, hooks, API calls, state, and types.

Section 04

services/

Backend services. Each is a separate deployable process.

Services
FolderPurposeTech
apiREST API — all business endpointsNestJS + Prisma
wsWebSocket gateway — real-time broadcastsSocket.IO
workerBackground jobs — refunds, cleanup, notificationsBullMQ
simulatorSimulation orchestrator — tick engine, scenariosNode + Turbo

Why services are separate

  • Each has different scaling characteristics (API is stateless, WS is stateful, worker is CPU-bound, simulator is tick-driven)
  • Each can be deployed independently
  • Failure in one doesn't crash the others
  • Turbo caches builds per service — CI runs only what changed
Section 05

engines/

Pure logic. No HTTP. No database. No side effects. Just functions.

Engines
FolderPurpose
trafficTraffic simulation — congestion, incidents
weatherWeather simulation — conditions, forecast
passengersVirtual passenger AI — behaviour, boarding
clockBusVerse Speed clock — simulation time source

Pure functions: engines take inputs and return outputs. They never touch the database, never call APIs, never read files. This makes them trivially testable and reusable from any service.

Section 12

Dependency Direction

One-way only. Never reverse.

apps/*         ──▶  packages/*
  │                    │
  ▼                    ▼
services/*     ──▶  engines/*  ──▶  packages/types
  │
  ▼
packages/sdk   ──▶  packages/types
Allowed Dependencies
LayerCan Depend OnCannot Depend On
appspackages, engines, sdkservices (direct), other apps
servicesengines, packagesapps, other services
enginespackages/types onlyservices, apps, other engines
packagespackages/typesservices, apps, engines
packages/typesnothinganything

Why one-way: if engines could import from services, a change in one service would force a rebuild of every engine that depends on it. One-way direction keeps builds fast and caches valid.

Section 13

Git Workflow Fit

How this structure maps to the three-branch model.

Branch → Folder Interaction
BranchWhat ChangesWhat CI Runs
feat/*One package or one app featureLint, typecheck, unit, build (only changed packages)
developIntegrated state of all packagesFull test suite + build + preview deploy
stagingVerified release candidateFull test suite + build + E2E + staging deploy
mainProduction-tagged buildFull suite + E2E + production deploy

Turbo caching: if a feature branch only touches apps/passenger-web, Turbo rebuilds only that app. The other four apps, four services, four engines, and five packages are skipped entirely. CI runs in seconds, not minutes.

Example feature branch workflow

git checkout develop
git pull origin develop
git checkout -b feat/seat-locking

# edit files in services/api/src/modules/seats/
# edit files in packages/types/src/booking.ts
# edit files in apps/passenger-web/src/features/seat-selection/

git add .
git commit -m "feat(booking): implement atomic seat lock acquisition"
git push -u origin feat/seat-locking

# Open PR into develop
# CI runs: lint + typecheck + unit + build for changed packages only
# Merge → develop
